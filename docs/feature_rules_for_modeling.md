# กฎ feature สำหรับโมเดลรายเดือน

เอกสารนี้สำหรับ **data scientist** ที่สร้าง feature และเทรนโมเดลจาก `data/model/province_month_unified` อ่านคู่กับ `docs/project_spec.md`, `data/model/README.md` และ `reports/data_quality_audit.md` (รายการ 2, 8, 9, 11)

ไปป์ไลน์ไม่สร้าง lag หรือ rolling mean ให้ สร้างเองตอนเตรียม feature จากตาราง unified ทั้งแผง ยังไม่เก็บเป็นตารางแยก ตัวช่วยที่ล็อกกฎ “ใช้ได้แค่เดือนก่อน t” คือ `build_forecast_features` ใน `src/model/leakage.py`

ทำนายเดือน `t` หมายถึง forecast ที่ตัดสินใจก่อนเดือน `t` จบ ใช้ข้อมูลถึง `t-1` เท่านั้น คำนวณ lag ก่อน แล้วค่อยตัดแถวถ้าจะตัด

## 1. Target

| รายการ | ค่า |
|---|---|
| ตาราง | `data/model/province_month_unified.parquet` (และ `.csv`) |
| Grain | 77 จังหวัด × เดือน, `province_id` เป็นสตริง 2 หลัก |
| ช่วง | **2018-01 .. 2025-12** (96 เดือน, 7,392 แถว, panel สมดุล) |
| Target | **`guest_arrivals_total`** (ผู้เข้าพักแรม, คน) |
| ไม่ใช่ target | `visitors_total` ไม่มีในตารางนี้ |

`visitors_total` อยู่ใน `data/core/province_month.parquet` เท่านั้น และเป็น **null ทุกแถวก่อน 2023-01** (4,620 แถว = 77 × 60 เดือน) ตั้งแต่ 2023-01 ถึง 2025-12 ครบ 2,772 แถว ห้ามเติม 0 ห้ามใช้เป็น target ของโมเดลรายเดือนชุดนี้

`guest_arrivals_thai` และ `guest_arrivals_foreign` ของเดือน `t` เป็นส่วนแยกของ target เดือนเดียวกัน ไม่ใช่ feature ของเดือน `t` **ปี 2018 ทั้งสองคอลัมน์เป็น null ทั้ง 924 แถว** เพราะ core มีแต่ยอดรวม ห้ามเติม 0

## 2. ห้ามใช้ยอดไตรมาสที่ครอบเดือน t

รายการ 9 ใน audit: ยอด `guest_arrivals` รายไตรมาสเท่ากับผลรวม 3 เดือนในไฟล์เดียวกัน ดังนั้นยอดไตรมาสนั้นรู้ค่าของเดือนที่กำลังทำนาย

ตรวจกับข้อมูลใน repo นี้แล้ว ส่วนต่างเป็น 0 ทุกแถว:

| แหล่ง | สิ่งที่เทียบ | ผล |
|---|---|---|
| `data/clean/mots_domestic_province/province_quarter` | `guest_arrivals_total` / `_thai` / `_foreign` เทียบผลรวม 3 เดือนใน `province_month` | 2,156 แถว (77 × 28 ไตรมาส, 2019-Q1 .. 2025-Q4) เท่ากันพอดี |
| ตารางเดียวกัน | `rain_sum_mm` เทียบผลรวม `rain_avg_mm` 3 เดือน | เท่ากันพอดี |
| `data/staging/mots/fact_tourism_long.parquet` | แถว `layout = quarterly_domestic`, `metric = guest_arrivals`, `area_level = province` | 7,392 แถวไตรมาส (2018–2025, `total` / `thai` / `foreign`) เท่ากับผลรวม 3 เดือนพอดี มีแถวรายเดือน 22,176 แถวที่นั่งคู่กับยอดไตรมาสซึ่งรวมเดือนนั้น |

`province_quarter` ไม่มีปี 2018 ยอดไตรมาส 2018 อยู่ใน staging และเท่ากับผลรวมเดือนเช่นกัน

กฎ: โมเดลที่ทำนายเดือน `t` **ห้ามใช้ยอดของไตรมาสที่บรรจุ `t`** และห้ามใช้ aggregate อื่นที่รวมเดือน `t` (ผลรวมทั้งประเทศของเดือน `t`, rolling ที่คลุม `t`, ผลรวมข้ามจังหวัดของเดือน `t`) ใช้ได้เฉพาะเดือน หรือไตรมาสทั้งก้อน ที่จบก่อน `t`

ตัวอย่างเชียงใหม่ (`province_id` `50`) 2024-Q2 จากตาราง unified ซึ่งตรงกับ `province_quarter`:

| เดือน | `guest_arrivals_total` |
|---|---:|
| 2024-04 | 617,125 |
| 2024-05 | 613,044 |
| 2024-06 | 580,513 |
| 2024-Q2 | **1,810,682** = ผลรวมพอดี |

ทำนาย **2024-05** แล้วใส่ยอด 2024-Q2 คือใส่ทั้งค่าเดือน พ.ค. และค่าเดือน มิ.ย. ที่ยังไม่เกิด ใช้ **2024-Q1** ได้ เพราะเดือนสุดท้ายคือ 2024-03 จะใช้ 2024-Q2 ได้เมื่อทำนายตั้งแต่ **2024-07** เป็นต้นไป

คอลัมน์อื่นใน `province_quarter` (`visitors_*`, `revenue_*`, `occupancy_rate_pct_total`, `rain_sum_mm`) ครอบ 3 เดือนเดียวกัน แม้ไม่ใช่ผลรวมของ target ก็ยังมีข้อมูลเดือน `t` ปนอยู่ ใช้กฎ “ไตรมาสต้องจบก่อน `t`” กับทุกคอลัมน์

ฟังก์ชัน `quarter_allowed_as_of` ใน `src/model/leakage.py` เป็นตัวตรวจนี้

## 3. กฎ leakage และ lag ที่ใช้

ชุด feature มาตรฐานของ forecast เดือน `t` มีเท่านี้:

| Feature | แหล่ง | หมายเหตุ |
|---|---|---|
| `guest_lag_1` | `guest_arrivals_total` ของ `t-1` | |
| `guest_lag_12` | `guest_arrivals_total` ของ `t-12` | seasonal naive ใช้ตัวเดียวกัน |
| `rain_lag_1` | `rain_avg_mm` ของ `t-1` | |
| `rain_roll3` | ค่าเฉลี่ย `rain_avg_mm` ของ `t-3`, `t-2`, `t-1` | หน้าต่างจบที่ `t-1` ถ้าเดือนใดเดือนหนึ่งหาย ให้เป็น null อย่าเฉลี่ยแค่เดือนที่เหลือ |
| `is_covid` | ธงปฏิทินของเดือน `t` | รู้ก่อนเดือนจบ ไม่ได้คำนวณจาก target |
| `is_covid_lag12` | `is_covid` ของเดือน `t-12` | ดูหัวข้อถัดไป |

Lag คำนวณจากตาราง unified ตอนสร้าง feature ไม่มีตาราง lag แยกใน repo **คำนวณบนแผงเต็มก่อน** รวมแถวปี 2018 และแถว COVID แล้วค่อยตัดแถวออกจาก loss ถ้า `groupby().shift()` หลังตัดแถว COVID แล้ว lag 1 ของ 2023-01 จะกลายเป็น 2020-02

`is_covid_lag12` มีเพราะ lag 12 ของปี 2021 ชี้ไปปี 2020 และ lag 12 ของปี 2023 ชี้ไปปี 2022 ซึ่งเป็นระดับผู้เข้าพักที่ถูกกดด้วยโควิด ไม่ใช่ฤดูปกติของปี 2018–2019 ธงนี้เป็น `is_covid` ของเดือน `t-12` โดยตรง

- ทั้งปี 2023: `t-12` อยู่ใน 2022-01 .. 2022-12 ซึ่งอยู่ในหน้าต่างโควิดครบ 12 เดือน ดังนั้น `is_covid_lag12` เป็นจริงทุกเดือน
- ปี 2021: จริงตั้งแต่ 2021-03 เป็นต้นไป (`t-12` คือ 2020-03 .. 2020-12) ส่วน 2021-01 และ 2021-02 ชี้ไป 2020-01 และ 2020-02 ซึ่งอยู่นอกหน้าต่าง ธงจึงเป็นเท็จ

ทางเลือกถ้าไม่อยากให้ lag 12 เป็นตัวแทนของระดับโควิด มีสองแบบ ไม่ได้อยู่ในชุดมาตรฐาน:

- **lag 24** ของ `guest_arrivals_total` เดือน 2021 ชี้ไปปี 2019 แต่เดือน 2023 ชี้ไปปี 2021 ซึ่งยังอยู่ในโควิดเป็นส่วนใหญ่ จึงไม่พ้นระดับที่ถูกกด
- **ค่าเฉลี่ยเดือนปฏิทินเดียวกันช่วงก่อนโควิด (2018–2019)** ใช้ได้เฉพาะเดือนที่ `< t` ตั้งแต่ 2020-01 เป็นต้นไป ทั้งปี 2018 และ 2019 อยู่ก่อน `t` สำหรับแถวปี 2019 ใช้ได้แค่ปี 2018 เพราะเดือนเดียวกันในปี 2019 คือ target

| สิ่งอื่น | กฎ |
|---|---|
| ฝนเดือนเดียวกับ t (`rain_avg_mm`, `rain_min_mm`, `rain_max_mm`) | **ค่าเริ่มต้นคือห้าม** ใช้ได้เฉพาะเมื่อทีมประกาศว่ารันนี้เป็น **nowcast** และแยกคะแนนออกจาก forecast |
| `visitors` ของเดือน t | ห้าม ทั้ง forecast และ nowcast เผยแพร่คู่กับผู้เข้าพัก |
| `guest_arrivals_thai` / `_foreign` ของเดือน t | ห้าม เป็นส่วนของ target |
| Scaler, encoder, target encoding | fit บนแถว train (`2019-01 .. 2022-12`) เท่านั้น ห้าม fit ทั้งแผง และห้าม fit รวม validation หรือ stream |

**ฝนเดือนเดียวกันยังเป็น pending decision** (audit รายการ 2) ทุกแถว 7,392 มีฝนและ `guest_arrivals` ของเดือนเดียวกัน ใน core มี `visitors_total` เดือนเดียวกันอีก 2,772 แถว ถ้ายังไม่มีการประกาศจากทีม ให้เทรนแบบ forecast (ฝนถึง `t-1`)

`visitors` ก่อน 2023-01 เป็น null ทั้งจังหวัด ถ้าจะใช้ lag ของ visitors ได้เฉพาะเดือนที่มีค่าจริง และต้องเป็นเดือนก่อน `t` ห้ามเติม 0

**Audit รายการ 8:** แถวรายเดือนปี 2023 ของ `visitors`, `guests`, `occupancy_pct`, `revenue_million_baht` ใน staging มาจากบล็อกปีก่อนในไฟล์ 2024 (`from_prior_year_column = true`) `guest_arrivals` ปี 2023 **ไม่ได้**มาจากบล็อกนั้น (`from_prior_year_column = false`, 2,772 แถว) target ในตาราง unified จึงไม่ใช่คอลัมน์ปีก่อน อย่าดึง visitors / occupancy / revenue / `guests` ปี 2023 จากบล็อกนั้นมาเป็นตัวเลขปฐมภูมิ

NSO ยังเป็น pending decision ใน `docs/project_spec.md` (แนวโน้มคือไม่ใช้) อย่า join เข้าตารางรายเดือนจนกว่าทีมจะรับ

## 4. COVID (2020-03 .. 2022-12)

`is_covid` เป็นจริงช่วง **2020-03 .. 2022-12** (34 เดือนต่อจังหวัด) ตาม `covid_window` ใน `config/sources.yaml`

การตัดสินของทีมสำหรับ split หลัก: **เก็บแถว COVID ไว้ใน train และใช้ `is_covid` เป็น feature** ช่วงนี้อยู่ใน train `2019-01 .. 2022-12` ทั้งก้อน

แถวที่ `guest_arrivals_total = 0` มี **27 แถว เป็นยอดจริง** ทั้งหมดอยู่ใน 2020-04, 2020-05 หรือ 2021-01 และ `is_covid = true` เก็บเป็น 0 ไม่ใช่ค่าหาย

ถ้าการทดลองภายหลังตัดแถวเหล่านี้ออกจาก loss ให้คำนวณ lag บนแผงเต็มก่อน อย่า `shift` หลัง drop

## 5. การแบ่งชุดข้อมูล

เดินตามเวลาเท่านั้น **ห้าม shuffle ห้าม random K-fold** วิธีหลักคือ split เดียวด้านล่าง ไม่ใช่ rolling-origin หลาย fold

`docs/project_spec.md` กำหนดว่าโมเดลรันแบบ online มี streaming replay สาย `2024-01 .. 2025-12` คือ replay นั้น

| ชุด | ช่วง | วิธีใช้ |
|---|---|---|
| Lag history | 2018-01 .. 2018-12 | **ไม่เทรน** มีไว้ให้ทุกเดือนของปี 2019 มี lag 12 (77 × 12 = 924 แถว) |
| Train | 2019-01 .. 2022-12 | เทรนที่นี่ รวม COVID 2020-03 .. 2022-12 และใช้ `is_covid` |
| Validation / test | 2023-01 .. 2023-12 | ปีแรกหลังหน้าต่างโควิด เลือกโมเดลที่นี่ |
| Online stream | 2024-01 .. 2025-12 | 24 เดือน ป้อนทีละเดือน คาด drift และ retrain ต้นปี 2024 ตอนท่องเที่ยวฟื้น |

Scaler และ encoder fit บนแถว train เท่านั้น แถวปี 2018 ไม่เข้า loss ค่าของมันโผล่ในโมเดลได้แค่ในฐานะ lag ของปี 2019

เลือกโมเดลและ hyperparameter จากคะแนนปี 2023 ถ้าจูนซ้ำบนปี 2023 หลายรอบ ให้รายงานผลของสาย **2024-01 .. 2025-12** (ต้นปี 2024 ต่อเนื่องไปปี 2025) เป็น test ที่ซื่อตรง อย่าใช้ปี 2023 รอบแล้วรอบเล่าแล้วเรียกมันว่า test

สายออนไลน์เดินทีละเดือน หลังเดือนหนึ่งถูก replay แล้ว เดือนนั้นเข้า history ของเดือนถัดไปได้ (feature ยังอ่านได้ถึง `t-1`) Retrain เมื่อเห็น drift ต้นปี 2024 ตามที่ project spec ไว้เรื่อง drift ห้ามเทรนบนทั้งช่วง 2024–2025 แล้วค่อยให้คะแนนย้อนหลัง

**ทำไมไม่ใช้ train 2019–2021 / validation 2022 / test 2023** Train ช่วง 2019-01 .. 2021-12 มีปี 2019 กับต้นปี 2020 นอกโควิด ส่วน 2020-03 .. 2021-12 (22 เดือน) เป็นระบอบโควิด การ fit จึงเรียนระดับที่ถูกกดเป็นหลัก Validation ทั้งปี 2022 ยังอยู่ในหน้าต่างโควิด (จบ 2022-12) การเลือกโมเดลจึงถูกให้คะแนนบนปีโควิดอีกปี และปี 2023 ซึ่งเป็นปีแรกหลังหน้าต่างจะถูกใช้ไปกับการทดสอบครั้งเดียวแทนที่จะใช้เลือกโมเดล Split ที่ทีมเลือกให้ train เห็นหน้าต่างโควิดครบพร้อม `is_covid` เลือกโมเดลบนปี 2023 และเหลือปี 2024–2025 เป็นสายที่การฟื้นตัวจะโผล่เป็น drift

Rolling-origin backtest เป็นการตรวจเพิ่มได้ แต่ไม่ใช่วิธีหลัก และไม่แทน split ด้านบน ถ้าจะรัน ยังต้องสร้าง feature จากเดือนที่มาก่อนเดือนที่ให้คะแนนเท่านั้น และห้าม shuffle

`scripts/model_readiness_check.py` แบ่ง train ≤ 2024 / test = 2025 และรายงาน MAPE เป็นการตรวจความพร้อมของข้อมูล **ไม่ใช่** โปรโตคอลในหน้านี้

## 6. Metrics

| Metric | บทบาท |
|---|---|
| **WAPE** | ตัวหลัก: `sum(\|y − ŷ\|) / sum(\|y\|)` |
| MAE | รายงานคู่กับ WAPE |
| RMSE | รายงานบนสเกลจำนวนคน สเกลนี้ถูกกรุงเทพฯ ดึง อย่าใช้แทน WAPE รายจังหวัด |
| MASE | MAE ของโมเดล หาร MAE ของ seasonal naive บนชุดเดียวกัน |
| MAPE | **ห้ามใช้เป็นตัวหลัก** แถวที่เป็น 0 ทำให้หารด้วยศูนย์ |

Seasonal naive ภายในจังหวัดคือ `ŷ_t = y_{t-12}` ซึ่งคือ `guest_lag_12` แถวที่ยังไม่มี `t-12` ไม่เข้าตัวหารของ MASE ตั้งแต่ 2019-01 เป็นต้นไป lag 12 มีค่า เพราะมียอดรวมปี 2018

รายงาน **WAPE รวมทั้งประเทศ และ WAPE รายจังหวัด** ทั้งบน validation ปี 2023 และบนสาย 2024–2025

Audit รายการ 11: กรุงเทพมหานคร (`province_id` `10`) เป็น **19.5%** ของ `guest_arrivals_total` ทั้งประเทศในช่วง 2018-01 .. 2025-12 จังหวัดที่มากที่สุดต่อค่ามัธยฐานของยอดจังหวัด ≈ 32.2 เท่า จังหวัดที่น้อยที่สุด ≈ 0.09 เท่า อย่าตัดจังหวัดใหญ่ทิ้งเพื่อให้ตัวอย่างสมดุล คะแนนที่พูลอย่างเดียวจะถูกกรุงเทพฯ ครอบงำ

## 7. Feature ที่อนุญาตและที่ห้าม

สถานะด้านล่างคือ **forecast** ของเดือน `t` แถว nowcast ใช้เฉพาะเมื่อทีมประกาศ และต้องไม่ปนกับตารางคะแนน forecast

| Feature | สถานะ | หมายเหตุ |
|---|---|---|

## 8. การขยาย date window ถึง 2025-12

งานนี้อยู่ใน PR #4 (`feat/unified-province-month`) หน้าต่างเดิมจบที่ **2025-08**

สิ่งที่เปลี่ยน:

1. `config/sources.yaml` ตั้ง `date_window.end` จาก `2025-08` เป็น `2025-12` (`date_window.start` ยังเป็น `2018-01`)
2. **ไม่ได้ดาวน์โหลดใหม่** Staging มีครบอยู่แล้ว: ฝน HII ใน `data/staging/hii/fact_rainfall.parquet` ไปถึง **2026-09** และ `guest_arrivals` รายเดือนของ MOTS มีครบ 77 จังหวัดใน **2025-09 .. 2025-12**
3. สร้าง core ใหม่ด้วยไปป์ไลน์เดิม `python -m src.core.build_core` ชื่อคอลัมน์ของ core ไม่เปลี่ยน `province_month` จาก **7,084 แถว** (77 × 92 เดือน ถึง 2025-08) เป็น **7,392 แถว** (77 × 96 เดือน ถึง 2025-12)
4. สร้างตาราง unified ใหม่ด้วย `python scripts/build_unified_province_month.py`
5. เทสเลิกฝังเลขหน้าต่างเดิม: `tests/test_qa_targets.py` อ่าน `date_window.end` จาก config แทนการตัดที่ `2025-08` และ `tests/test_data_quality_audit.py` นับจำนวนแถวของ `province_month` ที่สร้างแล้ว แทนสตริง `7084 rows`

ฝน HII หลัง 2025-12 (**2026-01 .. 2026-09**, 693 แถว) อยู่ใน staging เท่านั้น `build_core` ไม่ดึงเดือนที่เลย `date_window.end` เข้า core หรือตาราง unified

สร้างซ้ำจาก root ของ repo บน Windows (PowerShell) หลัง `date_window.end` เป็น `2025-12` แล้ว ไม่ต้องรัน ingest ซ้ำ:

```powershell

python scripts/build_unified_province_month.py
```

คำสั่ง core คือคำสั่งใน README และ `docs/pipeline_operators.md` คำสั่ง unified คือคำสั่งใน `data/model/README.md` path ใช้รูปแบบที่ `python` รับได้บน Windows ไม่มี separator ฝังในสคริปต์ (`pathlib`)
